# Постмортем: Сбой в работе GitHub 21 октября 2018 года
- Дата инцидента: 21-22 октября 2018 года
- Длительность: 24 часа 11 минут
- Статус: Завершено. Проведен полный анализ инцидента.

## Краткое описание инцидента (Executive Summary)
21 октября 2018 года в 22:52 UTC платформа GitHub столкнулась с серьезным сбоем, который привел к 24-часовой деградации сервисов. Инцидент был вызван потерей сетевого соединения между центром обработки данных (ЦОД) на Восточном побережье США и основным сетевым хабом во время плановых работ по замене оптического оборудования. Эта 43-секундная сетевая задержка запустила цепочку событий в автоматизированной системе управления базами данных (MySQL), что привело к рассинхронизации данных между ЦОДами на Западном и Восточном побережьях. В результате пользователи наблюдали устаревшую и противоречивую информацию (данные issues, pull requests не соответствовали реальному состоянию репозиториев), а также была недоступна обработка веб-хуков и сборка GitHub Pages. Критически важные данные Git (код) не пострадали. Восстановление полной функциональности и синхронизации данных заняло более 24 часов .

## Хронология событий (Timeline) (Все время указано в UTC)
22:52 - Начало инцидента. Во время плановых работ по замене 100G оптического кабеля происходит потеря связи между основным ЦОД на Восточном побережье и остальной сетью. Соединение прервано на 43 секунды. 
22:52 - 22:53 - Инструмент управления топологией MySQL, Orchestrator, развернутый в нескольких ЦОД и облаке, теряет связь с узлами в Восточном ЦОД. Благодаря алгоритму консенсуса Raft, оставшиеся узлы (в Западном ЦОД и публичном облаке) формируют кворум и инициируют автоматическое переключение (failover). Новым основным (primary) сервером для нескольких кластеров MySQL становится сервер в Западном ЦОД. Все новые записи начинают поступать туда. 
22:54 - Сетевое соединение восстановлено. Системы мониторинга GitHub фиксируют множественные ошибки. Приложения пытаются писать данные в новый primary на Западном побережье, в то время как старый primary на Восточном побережье все еще работает, но уже в статусе реплики. 
23:07 - 23:13 - Инженеры первой линии реагирования обнаруживают, что топология баз данных находится в неожиданном состоянии. Статус инцидента повышается до "желтого", а затем до "красного". К работе подключаются инженеры команды баз данных. Выясняется критическая проблема: данные, записанные в старый primary на Восточном побережье за несколько секунд до отключения, не были реплицированы на Западное побережье, а данные, накопившиеся в новом primary на Западном побережье за ~40 секунд, не могут быть реплицированы обратно на Восток из-за этого конфликта. 
23:19 - Принимается стратегическое решение: приоритет отдается целостности данных, а не скорости восстановления. Чтобы избежать дальнейшего повреждения данных, принудительно останавливается обработка веб-хуков, сборка GitHub Pages и другие фоновые задачи, которые могли бы создать противоречивые записи. 
00:05 (22 октября) - Инженеры принимают план восстановления, который заключается в восстановлении согласованного состояния путем подъема новых первичных баз данных на Восточном побережье из резервных копий и последующей репликации с Западного побережья. Начинается процесс восстановления из резервных копий, хранящихся в облаке. 
06:51 - Несколько меньших кластеров восстановлены из бэкапов в Восточном ЦОД и начинают догонять изменения с Западного ЦОД. Более крупные кластеры все еще восстанавливаются. 
11:12 - Все основные (primary) серверы баз данных переведены обратно в Восточный ЦОД. Производительность сайта значительно улучшается, однако множество читающих реплик все еще отстают от основных серверов на несколько часов. Пользователи видят несогласованные данные. 
13:15 - В часы пиковой нагрузки отставание реплик увеличивается. Инженеры разворачивают дополнительные читающие реплики в облаке на Восточном побережье, чтобы распределить нагрузку и дать репликации возможность догнать изменения. 
16:24 - Все реплики синхронизированы. Топология баз данных возвращается к исходному состоянию (primary на Востоке). 
16:45 - 23:03 - Команда приступает к обработке накопившейся очереди из более чем 5 миллионов веб-хуков и 80 тысяч сборок GitHub Pages. Процесс занимает несколько часов. В 23:03 UTC статус изменен на "зеленый", инцидент считается полностью устраненным. 

## Причины инцидента (Root Cause Analysis)
Сбой произошел из-за сочетания нескольких факторов, которые в совокупности создали "идеальный шторм" :

1. Триггер: Плановая работа с сетью (43-секундный сбой): Запланированная замена оборудования привела к временной, но полной потере сетевой связности между Восточным ЦОД и остальной инфраструктурой. Это само по себе не является ошибкой, но стало катализатором.
2. Автоматический failover в MySQL кластере: Инструмент Orchestrator, настроенный на автоматическое поддержание высокой доступности, корректно сработал на потерю связи с primary-сервером и инициировал выбор нового primary среди доступных реплик на Западном побережье.
3. Асинхронный режим репликации и потеря данных: Ключевая проблема. Для обеспечения производительности, GitHub использовал полусинхронную (semi-sync) репликацию MySQL. В момент сетевого сбоя, когда подтверждения от реплик перестали поступать, MySQL на старом primary (на Востоке) автоматически переключился в асинхронный режим, чтобы не блокировать запись. В результате за несколько секунд до полной потери связи и после неё, на старый primary было принято небольшое количество записей (например, 954 записи в самом нагруженном кластере), которые никогда не были отправлены на реплики, включая ту, что позже стала новым primary на Западе .
4. Split-brain (Расщепление сознания) на уровне данных: После восстановления сети возникла ситуация, когда два сервера (старый primary на Востоке и новый primary на Западе) приняли разные наборы записей, считая себя авторитетными. Это состояние "разделенного мозга" на уровне данных сделало невозможным простое переключение обратно или настройку репликации между ними, так как их истории транзакций разошлись.

## Последствия и воздействие (Impact)
1. Основное воздействие: Деградация сервисов, связанных с метаданными GitHub, хранящимися в MySQL. Пользователи не могли видеть актуальное состояние Issues, Pull Requests, комментариев. Сайт отображал несогласованную информацию.
2. Полная недоступность: Обработка веб-хуков и сборка GitHub Pages были полностью остановлены на время активной фазы восстановления.
3. Данные в безопасности: Критически важные данные — Git-репозитории (код) — остались нетронутыми и были доступны на протяжении всего инцидента .
4. Потеря данных: Официально заявлено, что потерянных данных нет. Однако несколько сотен транзакций, записанных в старый primary, потребовали ручного разбирательства и сверки с пользователями для восстановления .

## Что было сделано для восстановления (Resolution)
1. Приоритизация целостности: Первым делом была остановлена запись в уязвимые системы (веб-хуки, Pages) для предотвращения усугубления проблемы.
2. Восстановление из бэкапов: Основной стратегией стал подъем новых "чистых" primary-серверов на Восточном побережье из полных резервных копий.
3. Догоняющая репликация: После восстановления баз из бэкапов, они были настроены как реплики для нового primary на Западном побережье, чтобы втянуть все изменения, накопленные за время инцидента.
4. Масштабирование читающих реплик: Когда отставание реплик на Восточном побережье стало критическим и перестало уменьшаться из-за высокой нагрузки, были развернуты дополнительные реплики в облаке. Это позволило распределить нагрузку и дать репликации возможность догнать primary .
5. Обработка очередей: После полной синхронизации инфраструктуры началась контролируемая обработка накопившихся задач.

## Извлеченные уроки и дальнейшие действия (Lessons Learned & Action Items)
Этот инцидент выявил несколько критических областей для улучшения, которые GitHub обязался реализовать .
1. Архитектура и управление базами данных
Проблема: Автоматический cross-region failover опасен при асинхронной репликации, так как почти гарантированно ведет к потере данных или рассинхронизации.
Действия:
- Пересмотр автоматического failover: Отказ от полностью автоматического переключения primary-серверов между географически удаленными ЦОД. Сделать failover между регионами процессом, требующим ручного подтверждения (manual approval) после оценки рассинхронизации.
- Исследование глобальных транзакционных идентификаторов (GTID): Более широкое использование GTID для улучшения обнаружения и разрешения конфликтов репликации.
- Улучшение процесса восстановления: Разработка и тестирование более быстрых процедур восстановления согласованности данных, не требующих полного подъема из "холодных" резервных копий для всех случаев (например, использование pt-table-sync или других инструментов для точечного устранения расхождений).
2. Сетевая инфраструктура и отказоустойчивость
Проблема: Плановая работа с сетью привела к глобальному сбою из-за сильной связанности компонентов.
Действия:
- Улучшение планирования работ: Внедрение более строгих процедур для любых работ на сетевом оборудовании, соединяющем ЦОД, с предварительной оценкой рисков для систем HA.
- Тестирование хаоса (Chaos Engineering): Активное внедрение практик Chaos Engineering для регулярного тестирования реакции системы на внезапные отказы сети и узлов.
3. Процессы и коммуникация
Проблема: Коммуникация с пользователями во время инцидента была недостаточно точной, а оценки времени восстановления (особенно на основе линейной экстраполяции) оказались неверны.
Действия:
- Улучшение коммуникации: Разработка более качественных шаблонов для статусной страницы и блога, позволяющих быстро публиковать обновления даже при деградации внутренних инструментов (как GitHub Pages в этом инциденте).
- Более реалистичные ETA: Отказ от публикации жестких ETA (Estimated Time of Arrival) на основе неполных данных. Переход к указанию текущего статуса работ и следующих шагов, без привязки ко времени.
4. Обработка очередей
Проблема: После восстановления возникли проблемы с истечением срока действия (TTL) старых задач из очереди веб-хуков.
Действия: Внедрение более надежных механизмов обработки "захламленных" очередей после длительных инцидентов, включая возможность временного увеличения TTL или ручной очистки устаревших событий без остановки всей системы.
