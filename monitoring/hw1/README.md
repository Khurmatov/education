## Ответы к обязательным заданиям

1. Учитывая специфику проекта (HTTP-взаимодействие, вычислительная нагрузка на CPU, сохранение отчетов на диск), минимальный набор метрик должен охватывать четыре основных "золотых сигнала" (Google SRE) и специфику бэкенда: Traffic (Трафик), Latency (Задержки), Errors (Ошибки), Saturation (Насыщение).

Метрики, связанные с HTTP (золотые сигналы):
- Количество запросов в секунду (RPS): Показывает нагрузку на систему.
- Время ответа (Latency): Перцентили (p50, p95, p99) времени обработки запроса. Важно считать latency на стороне сервера (например, время выполнения хендлера).
- Коды ответов HTTP: Счетчики запросов, сгруппированные по кодам (2xx, 4xx, 5xx). Это позволяет отслеживать количество успешных операций и ошибок.

Метрики, связанные с вычислениями (Saturation/Errors):
- Загрузка CPU: Не просто средняя, а нагрузка на ядра (la), а также время, проведенное в системных вызовах (iowait), так как диск может быть узким местом.

Метрики, связанные с диском (Saturation/Errors):

- Загрузка диска (Disk I/O Utilization): Процент занятости диска, очередь запросов к диску (await, svctm). Это критично, так как отчеты сохраняются на диск.
- Свободное место на диске (inodes): Чтобы предотвратить ситуацию, когда отчеты не могут быть записаны из-за нехватки места.

Метрики "Проверка жизни" (Liveness):
- Uptime сервиса: Работает ли процесс.

Эти метрики позволяют ответить на вопросы: "Работает ли сервис?" (Uptime, HTTP 200), "Не падает ли он под нагрузкой?" (RPS, Latency), "Хватает ли ему ресурсов для вычислений и записи?" (CPU, Disk), и "Все ли в порядке с железом?" (inodes).

2. То, что видит инженер (RAM, CPU, inodes), для менеджера продукта (ПО) — это технические детали (сырые метрики). Ему нужны SLO (Service Level Objectives) — цели по уровню обслуживания, выраженные в понятиях, значимых для бизнеса и клиента.
Мы можем предложить ему SLI (Service Level Indicators) — измеримые показатели качества обслуживания, преобразованные из технических метрик:

Доступность (Availability):
- Техническая метрика: Коды HTTP 200.
- Бизнес-метрика (SLI): Процент успешных HTTP-запросов, которые привели к результату (формированию отчета).
- Как считать: (summ_2xx_requests) / (summ_all_requests).

Скорость работы (Performance):
- Техническая метрика: Время ответа в миллисекундах.
- Бизнес-метрика (SLI): Доля запросов, которые были выполнены быстро (например, быстрее 500 мс). ПО поймет это как "клиент не ждал слишком долго".
- Как считать: (count of requests with latency < 500ms) / (total requests).

Процент успешных вычислений:
- Техническая метрика: Логи приложения, ошибки сохранения файлов.
- Бизнес-метрика (SLI): Процент отчетов, которые успешно сформировались и сохранились.
- Как считать: (saved_reports) / (total_report_requests).

3. Ситуация типовая. Когда нет денег на централизованную систему типа Splunk или ELK (Elasticsearch, Logstash, Kibana), можно использовать бесплатные или встроенные механизмы.
Предлагаемое решение: Использование стека Loki + Promtail/Vector (Open Source) или Graylog.

Вариант А (Современный легковесный): Loki от Grafana Labs.
- Как работает: Promtail (агент) собирает логи с серверов и отправляет их в Loki. Loki хранит логи, сжимая их. Grafana используется для просмотра.
- Плюсы: Не требует индексации содержимого (как Elastic), что сильно экономит ресурсы. Легко интегрируется с уже имеющимся у вас Prometheus/Grafana (если вы его поставили в п.1). Бесплатно.

Вариант Б (Классический Open Source): Graylog.
- Как работает: Сервер приложений шлет логи (например, в формате GELF) прямо в Graylog, либо через побочный сборщик (sidecar).
- Плюсы: Готовый интерфейс, мощный поиск. Бесплатен.

Вариант В (Экстренный): S3 + Скрипты.
- Если совсем нет ресурсов на сервер для сбора логов, можно настроить ротацию логов (logrotate) на серверах приложений и складывать архивы в бесплатный S3-совместимый объектный стorage (или MinIO внутри компании). Разработчикам дать доступ к бакету. Но это костыль, поиск ошибок будет затруднен.

Вывод: Предложите развернуть Loki + Promtail. Это минимально затратно по ресурсам, быстро внедряется и решает задачу "видеть все ошибки".

4. Ошибка кроется в предположении, что все запросы, не вернувшие 4xx или 5xx, — успешные.
Формула summ_2xx_requests / summ_all_requests не учитывает 3xx редиректы.
Если в системе нет 4xx и 5xx, но SLA не поднимается выше 70%, значит, остальные 30% запросов — это 3xx (Redirection).

Это нормальная ситуация для многих приложений:
- Редиректы с / на /index.html.
- Редиректы с HTTP на HTTPS.
- Редиректы после логина.

Для корректного расчета "успешности" (Availability) обычно используют формулу:
(summ_2xx_requests + summ_3xx_requests) / summ_all_requests

Или, если мы считаем только успешные завершения бизнес-логики, нужно исключить не только 5xx/4xx, но и специфические 3xx, если они не являются частью успешного сценария. Но для общей картины доступности 3xx обычно приравнивают к успеху.

5. Pull модель (Система сама забирает метрики)

Плюсы:
- Проще контроль доступа: Мониторинг сам тянет данные, ему проще открыть firewall в одну сторону.
- Обнаружение сервисов (Service Discovery): Мониторинг сам знает, кого он должен опрашивать. Если таргет исчез — легко понять, что он умер.
- Централизованное управление: Настройки частоты сбора на стороне сервера.

Минусы:
- Сложность конфигурации: Нужно настроить Service Discovery или список таргетов.
- Проблемы с динамической инфраструктурой: Сложнее собирать данные с короткоживущих задач (batch-задачи, лямбды), которые уже завершились к моменту опроса.
- Нагрузка на сеть: Сервер мониторинга должен быть доступен для всех агентов.

Push модель (Агенты шлют данные в систему)

Плюсы:
- Простота настройки агентов: Агент знает только адрес, куда слать. Ему не нужно ждать запроса.
- Легко мониторить эфемерные задачи (jobs): Задача запустилась, отработала, отправила метрику и умерла.
- Надежность доставки: Агент может буферизировать метрики на диске, если центральный сервер недоступен.

Минусы:
- Сложность контроля доступа: Нужно открыть порт на прием на центральном сервере для всех агентов.
- Трудно отследить "смерть" таргета: Если агент перестал слать данные — то ли он умер, то ли просто сеть упала, то ли ему нечего слать.
- Нагрузка на агента: Агент тратит ресурсы на сериализацию и отправку.

6. 
- Prometheus — классическая Pull-модель. Сам ходит за метриками. Но есть Pushgateway для разовых задач (это надстройка, а не изменение парадигмы).
- TICK (Telegraf + InfluxDB) — в основе своей Push. Telegraf умеет работать в обоих режимах, но классическая связка подразумевает, что Telegraf пишет в InfluxDB.
- Zabbix — Гибридный. Может работать как в Pull (опрос агента сервером), так и в Push (активные проверки агента, trapper).
- VictoriaMetrics — Гибридный. Поддерживает Pull (как Prometheus), так и Push (принимает данные по протоколам InfluxDB, Graphite, OpenTSDB). Считается системой, которая "умеет всё".
- Nagios — классическая Pull. Плагины запускаются на сервере мониторинга (или через NRPE - удаленный запуск, что тоже вариация pull, когда центр инициирует проверку).
